wvd 1.1 v1.1.0 · 8a2b23b

2026-10-07 · 범위: 1.0 리뷰의 C1–C4, E2–E6 수정 · 배포는 1.2와 함께

프로세스 하나는 그대로 둔 채, 수집 경로가 어떤 잠금도 기다리지 않게 바꿨다. 1.0의 초 단위 정지는 사라졌지만 목표인 100 ms는 맞추지 못했다. 남은 원인이 GIL(E1)임을 측정으로 확인했고, 그래서 1.2에서 프로세스를 분리하게 됐다.

결정 사항변경 내용API 변화검증GIL 분석

결정 사항

질문결정
프로세스 분리(E1)를 1.1에 넣을지1.2로 미룬다. 부하 시험에서 100 ms를 못 맞추면 그때 분리한다. → 못 맞춰서 1.2에서 분리했다.
샘플에 gap_s 필드 추가추가한다. 필드만 늘어나므로 기존 클라이언트는 영향이 없다.
수집 스레드가 그래도 죽으면프로세스를 종료 코드 70으로 끝내서 systemd가 재시작하게 한다.
접근 제한 (E6)인증 없음(사내 시험용). 대신 무거운 조회만 동시에 2개로 제한하고, 30초 기다린 뒤 503을 준다.
버전·git7700c09에 v1.0.0 태그를 붙이고, v1.1 브랜치에서 작업한다. 패키지 버전은 1.1.0.

변경 내용

ID수정
C1읽기에서 나는 모든 예외를 잡아 연결을 끊고 재연결한다(termios.error 포함). 루프 전체도 except Exception으로 한 번 더 감싼다. 그래도 스레드가 끝나면 종료 코드 70으로 끝낸다. 처음 구현은 SIGTERM을 썼는데, systemd가 SIGTERM 종료를 정상 종료로 봐서 재시작하지 않았다. 그래서 server.should_exit 방식으로 바꿨다.
C2, E2
  • 수집 스레드는 읽기 → seq 부여 → 큐 → 게시만 한다. 잠금은 쓰지 않는다.
  • writer 스레드가 0.5초 단위로 묶어 기록하고, prune은 5천 행씩 짧은 트랜잭션으로 나눠 지운다.
  • 조회는 스레드마다 별도 SQLite 연결로 한다(WAL). 아직 기록되지 않은 구간은 링 버퍼에서 합쳐 넣는다.
  • 디스크가 5분 넘게 막히면 DB 기록분만 버리고 개수를 센다(db_dropped). 수집은 계속된다.
C3끝난 세션의 통계는 한 번만 계산해 sessions.stats에 저장한다. 세션 목록에 이 통계가 함께 담겨서, 대시보드는 목록 1건만 조회한다. 1.0은 1+15건을 조회했다.
C4모든 샘플에 직전 샘플과의 간격 gap_s를 넣는다. 주기의 2배를 넘으면 공백으로 센다. 0.5초 이상이면 sampler.gap 이벤트도 남긴다.
E3export는 1만 행씩 스트리밍하고 상한이 없다. history가 잘리면 "truncated": true를 붙인다. 통계는 한 번 훑어서 계산한다. 20만 샘플이 넘으면 p95는 일정 간격으로 뽑은 값에서 구한다(p95_stride).
E4구독자 큐를 약 5초분으로 줄였다. 넘치면 밀린 것을 모두 버리고 lag 메시지를 보낸다. SSE 연결 확인은 1초에 한 번만 한다.
E5health에 스레드 생존 여부, 공백 통계, DB 큐 상태를 추가했다. 스레드가 죽으면 status: down이 된다.
E6무거운 조회는 동시에 최대 2개. 나머지는 30초 기다린 뒤 503(Retry-After: 5)을 받는다.
기타
  • history 응답을 500개 단위로 나눠 직렬화한다. 한 번에 하면 json.dumps가 2만 샘플에 GIL을 160 ms 동안 잡고, FastAPI의 기본 변환에도 1초가 걸린다.
  • 종료 시 대기를 3초로 제한했다.
  • 부하 시험 tests/wvd_stress.py와 장애 주입 WVD_TEST_FAULT를 추가했다.

API 변화

  • 샘플: gap_s 필드 추가. CSV에서는 마지막 열이다.
  • /sensors/latest: age_s 추가
  • health: sampler_alive, writer_alive, fatal, last_sample_wall, gaps_total, max_gap_s_5m, last_gap, db_queue, db_dropped, stream_dropped 추가. status에 down 추가.
  • 스트림: lag 메시지 {"ts", "dropped"}
  • 이벤트: sampler.gap
  • 응답: 503 busy, history의 truncated, 통계의 max_gap_s와 p95_stride

검증

테스트 36개 통과. 1.0의 25개에 다음 11개를 더했다: termios 예외 재연결, 루프 예외 생존과 공백 이벤트, 스레드 사망 감지, DB 지연 중 수집 지속, 미기록 구간 합치기, 잘림 표시, export 스트리밍, 동시 실행 제한, 세션 통계 저장, lag 메시지, 통계 누적 계산. 실제 프로세스에서 수집 스레드가 죽으면 0.13초 뒤 종료 코드 70으로 끝나는 것도 확인했다.

GIL 분석과 시도한 완화책

py-spy로 측정해 보니, 무거운 조회 중에는 GIL이 전체 시간의 90% 동안 잡혀 있었다. 잡고 있는 코드는 대부분 순수 Python이다: 프레임 디코딩 36%, 통계 누적 21%, flatten 11%. 즉 C 코드가 한 번에 오래 잡는 문제가 아니라, 무거운 스레드 여럿이 GIL을 계속 나눠 차지하는 구조적인 경합이다.

시도결과조치
GIL 전환 간격 단축 (sys.setswitchinterval 1 ms, 0.5 ms)0.30–0.34 s, 효과 없음되돌림
GC 임계값 상향 (gen2 GC가 매번 50–100 ms를 쓰면서 회수량은 0)수집률 77% → 95%, 최대 공백은 0.2–0.4 s 그대로되돌림
JSON·CSV를 500개 단위로 나눠 직렬화GIL을 한 번에 160 ms 잡는 일이 사라짐반영
무거운 작업이 250개마다 GIL을 양보 (time.sleep(0))0.52 s로 악화. 양보한 GIL을 다른 무거운 스레드가 가져간다.되돌림
결론: 프로세스 안에서는 수집 스레드에 GIL 우선권을 줄 방법이 없다. 100 ms를 보장하려면 수집을 다른 프로세스로 떼어내야 한다. → 1.2
