1. 요약

seriesA에서 wvd는 단순한 기록기가 아니라 자동 중단(guard)의 유일한 데이터 소스입니다. 그래서 수집이 멈추면 두 가지 결과 중 하나가 생깁니다. guard가 잘못 중단시키거나(오작동), guard가 커넥터 상태를 못 보는 구간이 생기거나(안전 공백)입니다.

2. 현재 사용 구조

빨간 상자와 점선이 병목입니다. 수집 스레드와 API 조회가 같은 잠금을 놓고 경쟁하고, 같은 GIL 아래에서 돕니다.

수집과 API는 이미 서로 다른 스레드에서 돌고 있습니다(wvd-sampler 스레드, uvicorn 이벤트 루프, 스레드풀). 그래서 문제는 스레드 분리 여부가 아니라 공유 자원, 즉 저장소 잠금, SQLite 연결 하나, GIL입니다.

3. 확인된 문제

C1. USB 재연결 시 수집 스레드가 죽음 미수정

  • 증상: 16:10에 WireView가 ttyACM0에서 ttyACM1로 다시 잡혔습니다. 이때 수집 스레드가 termios.error: (5, 'Input/output error')로 종료됐습니다. HTTP는 계속 살아 있어서, 16:10:52의 마지막 값을 최신 값처럼 계속 응답했습니다.
  • 원인: transport.transact()의 termios.tcflush()가 termios.error를 던집니다. 그런데 sampler._run()은 except (OSError, DeviceError)만 잡습니다. termios.error는 OSError의 하위 클래스가 아니라서(서버에서 확인) 예외가 스레드 밖으로 빠져나가고, 스레드가 그대로 끝납니다. 재연결 로직(_connect)은 실행되지 않습니다.
  • 현황: 배포본(/opt/wvd)과 저장소 코드가 같고, 커밋도 7700c09 이후 없습니다. 오늘 16:52 이후에는 재연결이 없어서 다시 드러나지 않았을 뿐입니다.
  • seriesA 영향: guard가 5초 무수신으로 중단시키므로 안전 쪽으로는 막힙니다. 다만 야간 실행이 거기서 끝나고, 사람이 wvd를 재시작해야 합니다.

  • 잠금이 풀린 뒤에도 build_sample 디코딩과 compute_stats가 순수 Python으로 GIL을 오래 점유합니다(E1).

C3. 세션 기능이 C2를 유발

  • POST /sessions/{id}/stop은 세션 전체 구간에 대해 compute_stats(store.range(...))를 동기로 계산합니다.
  • 세션이 시작되거나 끝날 때마다 hub.publish({"kind": "session"})가 나갑니다. 대시보드는 이 이벤트를 받으면 /sessions?limit=15를 조회한 뒤 세션마다 /sessions/{id}(전체 구간 통계)를 요청합니다(wvd/static/app.js:381). 대시보드 수 × 세션 15개 × 세션 길이만큼 비용이 커집니다.
  • 대시보드를 새로 열 때도 같은 요청이 나갑니다. A3(3시간, 54만 샘플)이나 A4(8시간) 세션이 있었다면, 누가 대시보드를 열 때마다 부하 도중에 수십 초씩 수집이 멈췄을 것입니다.
  • 조치: seriesA는 세션을 쓰지 않도록 바꿨고, 이미 생긴 seriesA 세션 4개는 삭제했습니다(2026-10-07 20:1x).

C4. 수집 정지 = 데이터 손실

수집 루프는 밀리면 따라잡지 않고 다음 주기로 다시 맞춥니다(if next_tick < now: next_tick = now). 기기도 값을 쌓아 두지 않으므로(약 16 ms마다 갱신) 멈춘 동안의 측정값은 사라집니다. 예를 들어 4.46초 공백이면 약 220 샘플이 빠집니다. 분석의 1초 평균에도 공백이 생깁니다.

4. 예상되는 문제

E1. 스레드를 나눠도 GIL 경합은 남음

  • 수집 스레드는 이미 따로 있지만, 같은 프로세스 안이라 GIL을 공유합니다.
  • compute_stats, build_sample 디코딩, CSV·JSON 생성처럼 순수 Python으로 무거운 작업이 돌면 수집 스레드가 GIL을 얻기까지 지연됩니다. 기본 전환 간격은 5 ms이지만 여러 스레드가 경쟁하면 길어집니다.
  • 잠금 문제(C2)를 고치면 초 단위 정지는 사라질 것으로 보입니다. 다만 수십~수백 ms 지터는 남을 수 있습니다.
  • 50 Hz 수집을 확실히 보장하려면 수집을 별도 프로세스로 분리하는 편이 확실합니다.

E2. 수집 스레드가 DB 기록과 정리까지 직접 수행

  • 0.5초마다 flush()(BEGIN, executemany, COMMIT)와 60초마다 _prune()이 수집 스레드 안에서 잠금을 잡고 실행됩니다. 디스크 I/O 지연, WAL 체크포인트, 긴 DELETE가 그대로 수집 정지로 이어집니다.
  • _prune은 세션 구간에 속한 샘플을 지우지 않습니다(NOT EXISTS … sessions). 72시간이 지나 실제 삭제가 시작되면 행마다 상관 서브쿼리가 돌아 비용이 커질 수 있습니다. 아직 72시간 운용 전이라 확인되지 않았습니다.

E3. 긴 구간 내보내기의 조용한 잘림과 메모리

  • store.range()는 LIMIT MAX_QUERY_SAMPLES(500,000)로 잘립니다. 50 Hz에서는 약 2.8시간입니다. 응답에는 잘렸다는 표시가 없습니다.
  • 그래서 8시간 세션의 CSV 다운로드나 /export?last=8h는 앞부분 2.8시간만 담깁니다. seriesA는 1분 단위로 나눠 받아서 영향이 없지만, 대시보드에서 받는 CSV는 해당됩니다.
  • 내보내기는 전체 CSV를 메모리(StringIO)에서 만든 뒤 한 번에 보냅니다. 50만 행이면 수백 MB이고, 만드는 동안 GIL을 점유합니다(E1).

E4. 실시간 스트림 큐가 커서 생기는 지연

  • 구독자 큐는 2000개이고, 50 Hz에서 40초분입니다. 구독자가 느리면 버리기 전에 최대 40초 늦은 데이터를 받습니다. 버리는 경우에도 클라이언트에 알리지 않습니다.
  • guard는 "마지막으로 받은 시각"으로 정지를 판단합니다. 그래서 늦게 도착한 오래된 샘플을 최신으로 믿을 수 있습니다. seriesA 쪽에서 샘플 시각(ts) 기준 지연 검사를 추가할 예정입니다(7장).
  • SSE 루프는 메시지마다 await request.is_disconnected()를 호출합니다. 50 Hz × 클라이언트 수만큼의 부담이 생깁니다.

E5. health가 이상을 드러내지 않음

  • measured_hz는 최근 50개 샘플 기준이라 순간적인 정지는 금방 묻힙니다. 최대 공백, 공백 횟수, 수집 스레드 생존 여부는 제공하지 않습니다.
  • C1처럼 스레드가 죽었을 때 connected와 last_sample_age_s가 어떻게 보이는지 확인이 필요합니다. 스레드가 죽어도 device 객체는 남아 있어서 connected=true로 나올 가능성이 있습니다.

E6. 인증 없이 모든 인터페이스에 열려 있음

  • 0.0.0.0:8765에 토큰이 없습니다. 같은 네트워크의 누구나 세션 생성·삭제, 긴 구간 조회, 내보내기를 할 수 있습니다.
  • 악의가 없어도 무거운 요청 하나가 C2를 일으켜 guard의 데이터 소스를 끊을 수 있습니다. 안전장치가 의존하는 서비스로서는 위험합니다.

E7. DB 크기

3시간에 93 MB가 쌓였습니다. 선형으로 추정하면 72시간 보관 시 약 2.2 GB입니다. 여기에 세션 구간의 샘플은 무기한 보관됩니다. ts 인덱스가 있어서 구간 검색 자체는 괜찮지만, 반환 행 수에 비례하는 fetch와 디코딩 비용은 그대로입니다.

6. 수정 검증 방법

수정 후 아래 시험을 통과하면 야간 실행의 전제 조건을 만족한 것으로 봅니다. 부하 생성 스크립트(tests/wvd_stress.py)는 요청하시면 seriesA 쪽에 만들어 두겠습니다.
